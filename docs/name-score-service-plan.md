# 이름 점수 확인 서비스 — 상세 기획서

> 이 문서는 무료 "이름 점수 확인하기" 서비스의 제품 기획을 정리한다. 도메인 규칙·기술 결정의 단일 기준 문서는 `CLAUDE.md`(3.10, 0.1)이고, 디자인 규칙은 `design.md`(6장)다. 이 문서는 그 결정들을 제품 관점에서 한데 모아 설명한다 — 규칙이 바뀌면 `CLAUDE.md`/`design.md`를 먼저 고치고 이 문서를 갱신한다.

---

## 1. 배경 / 목적

기존 "유어네임"은 사주 분석 기반 정통 작명 리포트를 제공하는 유료 컨셉의 단일 서비스였다. 서비스의 정확성과 신뢰도는 이미 검증됐지만(Phase 1~6), 유료 서비스만으로는 신규 사용자가 결제 이전 단계에서 서비스 품질을 체감할 방법이 없었다.

**"이름 점수 확인하기"**는 이미 지어진 이름(보통 부모가 이미 짓고 출생신고까지 마쳤거나 후보로 고민 중인 이름)의 점수를 무료로 즉시 알려주는 기능이다. 목적은 두 가지다.

1. **사용자 확보(유입 채널)**: 결제 장벽 없이 서비스의 계산 엔진 품질(발음오행·수리사격·자원오행 등 결정적 계산)을 직접 체감하게 한다.
2. **유료 전환 퍼널**: 점수 결과 화면 하단에 "더 완벽한 이름을 원하신다면" 카드로 프리미엄 "아기 이름 짓기"(`/naming`)를 자연스럽게 소개한다. 특히 점수가 낮게 나오거나 경고(인명용 아님/불용문자)가 뜬 사용자는 개명·재작명 니즈로 이어질 가능성이 높다.

**핵심 제약**: 무료 서비스는 **운영자 금전 부담이 0이어야 한다.** 기존 유료 파이프라인은 매 요청마다 Claude API(`lib/llm/explain.ts`)를 호출해 크레딧 비용이 발생하지만, 채점 서비스는 이미 `lib/naming/`에 구현·검증된 결정적 계산 함수(발음오행, 81수리, 오행 분포, 용신, 만세력)를 재사용해 **LLM을 전혀 호출하지 않는다.** 발생하는 비용은 Turso DB 읽기뿐이며, 9,063자 규모의 한자 테이블 조회는 무료 티어로 충분하다.

## 2. 두 서비스 비교

| | 이름 점수 확인하기 (무료) | 아기 이름 짓기 (프리미엄) |
|---|---|---|
| 라우트 | `/score` | `/naming` |
| 입력 | 생년월일시 + 성씨(한자 포함) + **이미 정해진 이름 한자 2글자** | 생년월일시 + 성별 + 성씨 |
| 출력 | 점수(0~100) + 등급(S~D) + 항목별 근거 + 경고 배지 | 이름 후보 3~5개 + LLM 해설 리포트 |
| 엔진 | `lib/naming/score.ts` (채점 — 등급 매김) | `lib/naming/candidates.ts` (생성 — 하드 필터 탐색) |
| LLM 사용 | **없음** | Claude API (`claude-opus-4-8`) — 해설·순위 큐레이션 |
| 성별 입력 | 불필요 (채점에 영향 없음) | 필요 (`given_name` 큐레이션 풀 선택용) |
| 비용 구조 | DB 읽기만 (사실상 0원) | DB 읽기 + LLM 토큰 비용 (요청당 발생) |
| 처리 시간 | 즉시(수십~수백 ms, DB 조회+순수 계산) | LLM 응답 대기 필요(수 초) |

두 서비스는 같은 결정적 계산 엔진(사주 계산, 오행 분포, 용신 도출, 만세력)을 공유한다. 차이는 "이름을 만드는가(생성) vs 이미 있는 이름을 평가하는가(채점)"이며, 이 차이 때문에 하드 필터(생성)와 가중합 등급제(채점)라는 서로 다른 알고리즘이 필요하다(4절).

## 3. 사용자 플로우

```
랜딩(/) ─┬─▶ [이름 점수 확인하기] 카드 클릭 ─▶ /score
         └─▶ [아기 이름 짓기] 카드 클릭     ─▶ /naming
```

`/score` 내부 플로우 (4단계 위저드 → 로딩 → 결과):

1. **기본 정보**: 한글 성씨 입력 (동자이음 성씨면 한자 선택 단계 추가)
2. **생년월일**: 양력/음력·윤달, 년/월/일
3. **태어난 시각**: 시/분, 또는 "정확한 시각 모름" 체크(낮 12시로 계산)
4. **이름 한자**: 이름 두 글자 각각 "한자 찾기"(한글 음 검색 → 후보 목록 → 선택)로 입력
5. **제출** → 로딩(사주팔자 계산 → 오행·용신 계산 → 채점, 3단계 스테이지 연출) → **결과 화면**

결과 화면 구성(위→아래, 점진적 공개):
1. 헤더: 성씨+이름 한자, "다시 확인" 버튼
2. 점수 카드: 큰 점수 숫자 + 등급 배지 + 등급 설명 문구, 경고 배지(있을 때만)
3. 항목별 점수: 발음오행/수리사격/자원오행/음양 4개 막대 + 발음오행 흐름 상세 + 수리사격 4격 상세
4. 만세력 상세 표(`ManseryeokTable` 재사용 — 십신·지장간·공망)
5. 사주 요약(오행 분포 차트 + 용신)
6. 유료 서비스 유도 카드
7. 법적 고지

## 4. 채점 로직 상세

`CLAUDE.md` 3.10에 확정된 규칙의 제품 언어 재서술이다.

### 4.1 왜 하드 필터가 아니라 등급제인가

프리미엄 서비스의 후보 **생성** 엔진은 "발음오행이 전부 순방향 상생 + 4격이 전부 81수리 길수"인 이름만 만든다(하드 필터). 하지만 이미 지어진 실제 이름은 이 기준을 정확히 만족하지 않는 경우가 매우 흔하다 — 부모가 다른 기준(어감, 항렬자, 가족 전통 등)으로 지었을 수 있기 때문이다. 하드 필터를 그대로 채점에 쓰면 대부분의 실제 이름이 "0점 불합격"이 되어 서비스가 무의미해진다. 그래서 채점은 **가중합 등급제**를 쓴다 — 조건을 얼마나 충족하는지 정도의 차이를 점수로 보여준다.

### 4.2 가중치 (100점 만점)

| 항목 | 배점 | 판정 근거 |
|---|---|---|
| 발음오행 상생 | 30점 | 성→이름1→이름2, 인접 두 관계 각 15점 |
| 수리사격(4격) | 40점 | 원격·형격·이격·정격 각 10점, 81수리 길흉 |
| 자원오행 용신 일치 | 20점 | 이름 두 글자 각 10점, 한자 부수 오행이 용신과 일치하는지 |
| 음양 배열 | 10점 | 성+이름 획수의 홀/짝이 한쪽으로 쏠리지 않는지 |

### 4.3 발음오행 4단계 등급

기존 생성 엔진은 "순방향 상생만 통과, 나머지 전부 탈락"이었지만, 채점은 오행 관계를 4단계로 나눠 점수 차등을 둔다.

| 등급 | 의미 | 배점 비율 |
|---|---|---|
| 상생 | 앞 글자가 뒤 글자를 순방향으로 생함(예: 金→水) | 100% (15점) |
| 비화 | 두 글자 오행이 같음 | 50% (7.5점) |
| 역상생 | 뒤 글자가 앞 글자를 생함(방향만 반대, 생하는 관계 자체는 유지) | 50% (7.5점) |
| 상극 | 어느 한쪽이 다른 쪽을 파괴함(양방향 모두 상극으로 처리) | 0% (0점) |

예시: 성 金 → 이름 "미가"(水→木)라면 金→水(상생)·水→木(상생)으로 30점 만점.

### 4.4 자원오행 미배속(NULL) 처리

한자의 부수→오행 배속표는 214부수 중 18개만 채워진 **의도적으로 부분적인 표**다(`CLAUDE.md` 3.5). 이름 두 글자 중 자원오행이 없는(NULL) 글자는 이 항목에서 판단 자체를 보류한다. 두 글자 다 NULL이면 자원오행 항목(20점)을 총점 분모에서 제외하고, 나머지 80점 만점을 기준으로 100점으로 재환산한다 — "자원오행을 몰라서 0점"이 아니라 "이 기준으로는 평가하지 않음"으로 취급한다.

### 4.5 등급(S/A/B/C/D)

| 점수 | 등급 |
|---|---|
| 90~100 | S |
| 80~89 | A |
| 65~79 | B |
| 50~64 | C |
| 0~49 | D |

등급은 새로운 판정이 아니라 이미 계산된 점수를 보기 쉽게 구간화한 표시 값이다.

### 4.6 인명용 한자 / 불용문자 — 점수 아님

두 조건은 점수에 반영하지 않고 별도 경고로만 표시한다: 인명용 한자 목록에 없으면 "출생신고 시 한글로만 기록될 수 있음" 경고, 불용문자면 그 사유를 함께 보여준다. 이는 "이름의 좋고 나쁨"이 아니라 "실사용·신고 가능 여부"에 대한 사실 안내이기 때문이다.

## 5. 화면별 요구사항

디자인 세부 규칙은 `design.md` 6장을 따른다. 핵심만 요약한다.

- **랜딩**: 계산 로직 없는 두 카드(무료/프리미엄 배지로만 구분, 동일한 카드 스타일).
- **입력 폼**: 기존 `InputForm`과 시각적으로 동일한 위저드 톤(단계 인디케이터, 카드 상단 액센트 바). "한자 찾기"는 검색→목록→선택의 3단 흐름이며, 인명용 아님/불용문자 한자도 목록에서 숨기지 않고 경고 배지로 표시(사용자가 실제로 쓰는 한자가 등록 목록 밖일 수 있으므로).
- **결과 화면**: LLM 산문이 없으므로 점수 숫자(56px, 리포트에서 가장 큰 타이포)와 막대 그래프·배지로 전문성을 표현한다. "AI가 없어서 부실해 보이는" 인상을 주지 않는 것이 핵심 디자인 목표(design.md 0장).

## 6. API 스펙

### `POST /api/score`

```jsonc
// Request
{
  "year": 2024, "month": 3, "day": 15, "hour": 10, "minute": 30,
  "isLunar": false,
  "surnameHangul": "김", "surnameHanja": "金", // 동자이음 성씨면 필수
  "givenName": [
    { "hangul": "서", "hanja": "序" },
    { "hangul": "준", "hanja": "俊" }
  ]
}
```

```jsonc
// Response 200
{
  "saju": { /* Saju */ },
  "elementDistribution": { /* ElementDistribution */ },
  "yongsin": { /* YongsinResult */ },
  "manseryeok": { /* Manseryeok */ },
  "surname": { /* Surname */ },
  "givenName": [ /* Hanja, Hanja */ ],
  "score": {
    "totalScore": 83,
    "grade": "A",
    "categories": [ /* ScoreCategoryResult × 4 */ ],
    "phoneticLinks": [ /* PhoneticLinkResult × 2 */ ],
    "numerology": [ /* NumerologyGyeokScore × 4 */ ],
    "warnings": [ /* ScoreWarning[] */ ]
  }
}
```

- 400: 필수 필드 누락, 미등록 성씨/한자, 성씨 한자 특정 필요(동자이음), 유효하지 않은 한글 음절.
- LLM 호출 없음 — Anthropic API 관련 지연·비용이 이 경로에는 전혀 없다.

### `GET /api/hanja-search?reading=<한글 1글자>`

```jsonc
// Response 200
{ "hanja": [ /* Hanja[] — is_name_allowed DESC, is_common DESC, stroke_original ASC 정렬 */ ] }
```

- 계산 없는 단순 DB 조회. `is_name_allowed`/`is_forbidden`으로 필터링하지 않고 전부 반환(정렬만 유효한 것을 위로).

## 7. 데이터/비용 영향

- 새 DB 테이블·컬럼 없음 — 기존 `hanja`/`surname`/`numerology_81`만 조회.
- `lib/db.ts`에 조회 함수 1개(`getHanjaByReading`) 추가. 인덱스 없이 `json_each`로 풀스캔하지만 9,063행 규모라 실사용에 문제없다.
- **LLM 비용 0** — `/api/score`, `/api/hanja-search` 어디에도 Anthropic SDK 호출이 없다(코드 구조상으로도 `lib/naming/`은 8.1 원칙에 따라 애초에 LLM을 import할 수 없다).
- Turso 읽기 요청만 늘어나며, 무료 티어 한도 안에서 충분히 처리 가능한 규모다.

## 8. 한계 및 리스크

- **한자 필수 입력 장벽**: 이름의 한자를 모르는 사용자는 서비스를 이용할 수 없다(AskUserQuestion으로 확정된 결정 — 한자 없이는 원획 기반 수리사격·자원오행 계산이 불가능하므로 정확도를 위해 필수로 뒀다). "한자 찾기" UI로 완화하지만, 애초에 한자 이름이 없는 순한글 이름(예: "하늘", "이슬")은 채점 대상에서 제외된다.
- **GIVEN_NAME_LENGTH=2 제약**: 1글자·3글자 이상 이름은 이번 범위에서 채점할 수 없다(기존 생성 엔진과 동일한 제약을 그대로 이어받음).
- **상극 등급 판정은 이번에 신설된 규칙**: 발음오행 4단계 등급(상생/비화/역상생/상극)은 기존 생성 엔진의 하드 필터(통과/탈락)를 확장해 새로 설계한 것이라, 다른 유파의 수리성명학 채점 기준과 정확히 일치하지 않을 수 있다. 실사용 피드백이 쌓이면 배점 비율(현재 상생 100%/비화·역상생 각 50%/상극 0%) 재조정이 필요할 수 있다.
- **자원오행 커버리지 33% 미만**: 9,063자 중 약 33%만 자원오행이 배속돼 있어(`CLAUDE.md` 3.5), 많은 이름이 자원오행 항목 재환산(4.4)을 거친다 — 이 항목의 변별력이 이름마다 들쭉날쭉할 수 있다.
- **가중치 자체가 실사용 데이터 없이 정한 초기값**: 발음30/수리40/자원20/음양10은 사용자와 협의해 정한 첫 배정이며(`CLAUDE.md` 6장과 동일하게, 실사용 피드백이 쌓이면 재조정 대상).

## 9. 향후 확장 (미결정)

- **유료 결제 게이트 실제 연동**: 이번 범위 밖이다. 현재 `/naming`은 "프리미엄"이라는 개념만 있을 뿐 코드베이스에 결제 시스템 자체가 없다(로그인·과금·사용량 제한 전부 미구현). 무료→유료 전환을 실제 매출로 연결하려면 별도 결제 연동 프로젝트가 필요하다.
- **이름 후보 풀 확장이 채점에 미치는 영향**: `given_name`(3.7) 큐레이션 풀이 커지면 유료 서비스의 생성 결과는 달라지지만, 채점 서비스는 이 풀을 아예 쓰지 않으므로(2절 표 참고) 영향이 없다 — 단, 채점 결과에 "이 이름은 실사용 빈도가 어느 정도인지"를 함께 보여주는 기능을 추가하려면 `given_name` 조회를 채점 파이프라인에도 연결하는 별도 결정이 필요하다.
- **무료 서비스 사용량 계측**: 전환 퍼널 가설(1절)을 검증하려면 `/score` 완료 수 → `/naming` 유입 클릭률 계측이 필요하지만, 이번 범위에는 분석 도구 연동이 포함되지 않았다.
